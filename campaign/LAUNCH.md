## Objective

Turn 59 separate repositories into one legible body of work, then convert attention into repository visits, stars, issues, reproductions and independent submissions.

## Positioning

**Typed decisions. Real software.**

The campaign leads with concrete software problems rather than the model. Every post follows the same order:

1. Familiar engineering problem.
2. Working artifact.
3. Evidence or explicit boundary.
4. Repository link.
5. One focused question.

## Ten-day momentum sprint

The launch is deliberately compressed while Jev is new. Publish the launch thread immediately, then two substantial posts per day for ten days. Each post must carry a distinct artifact, result, architecture or audience; do not repeat the same announcement copy.

| Day | Morning — proof/demo | Late afternoon — angle/roundup |
| --- | --- | --- |
| 1 | Launch thread + ecosystem map | Jev Rerank benchmark |
| 2 | DecisionPacks offline demo | Why version decision contracts |
| 3 | Jev Proxy MCP flow | Agent safety roundup |
| 4 | Jev Screen workflow | Research tools roundup |
| 5 | Jev Codebook review loop | Human-in-the-loop design note |
| 6 | Jev Utility thresholds | Calibration and mistake-cost note |
| 7 | VS Code or Figma screen demo | Native tools roundup |
| 8 | Légifrance Impact demo | France/public-data roundup |
| 9 | DecisionOps or TimeMachine | Evals and policy replay roundup |
| 10 | Best failures and boundaries | Community submissions + next build vote |

Target windows in Europe/Paris: 09:00–10:00 and 17:00–18:30. If a post is still receiving substantive replies, delay the next one rather than splitting the conversation.

## Daily operating rhythm

- Publish one proof-bearing post in the morning.
- Spend 30–45 minutes replying to relevant Jev, agent, RAG and structured-output conversations.
- Publish a complementary technical angle or roundup in the late afternoon.
- Respond to every substantive question on the launch posts the same day.
- Quote-post only when adding a benchmark, reproduction or implementation detail.

Do not publish thirty near-identical links. One strong post per project is earned by a working demo, result or lesson.

## After the sprint

Move to four posts per week for six weeks: one hero demo, one code/architecture post, one measured result or boundary, and one themed roundup or community project.

Primary success metric: meaningful external actions per 1,000 impressions, where meaningful means a star, issue, pull request, reproduction or project submission.
